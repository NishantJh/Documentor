# Documentor Implementation Plan

## Mission

Build a Windows-first, evidence-backed documentation engine that continuously records how a multi-machine homelab is configured and generates ordered, reproducible setup and recovery procedures. Preserve raw evidence while excluding reverted experiments from the primary procedure when evidence supports doing so.

## Core principles

- Windows is the primary activity recorder; most administration starts there.
- Remote hosts provide authoritative state snapshots and diffs.
- Raw evidence is append-only; generated documentation is a derived, reviewable artifact.
- A diff describes state changes, not necessarily the commands or causal sequence.
- Every important claim should link to its evidence and be labelled observed, inferred, or tested.
- Never mark a recovery procedure tested unless it has actually been validated.
- Do not execute commands received from collectors or generated by the model automatically.
- Redact credentials and sensitive data before storage or upload.
- GitHub contains source and sanitized examples only, not live homelab evidence.

## Target environment

- Windows workstation: primary recorder and operator interface.
- Proxmox: central service in a dedicated Debian LXC.
- Homelab targets: Unraid, Proxmox hosts and guests, Incus, OpenWrt router/APs, Docker services and other supported systems.
- Repository: https://github.com/NishantJh/Documentor
- Central service: FastAPI, SQLite and filesystem evidence storage.
- Documentation: Markdown with relative links to retained evidence.
- AI: pluggable local Ollama or remote API provider; provider integration must be explicit and secret-safe.

## Architecture and data layers

1. **Collectors:** Windows activity and inventory; remote APIs, SSH-based read-only collection and native configuration exports.
2. **Raw evidence ledger:** timestamped events, command metadata, bounded outputs, screenshots, logs, and references to configuration snapshots. Preserve provenance.
3. **Snapshots and diffs:** normalized, timestamped configuration state per host/subsystem, with redaction and stable identifiers.
4. **Reconciliation engine:** correlate events with state transitions; classify actions as retained, reverted, superseded, failed or uncertain.
5. **Documentation generator:** maintain machine inventory, service reference, ordered setup procedures, troubleshooting and recovery guides.
6. **Validation engine:** run only explicitly approved, safe checks; record expected and actual results.
7. **Interface and operations:** search, review, edit, approve, export, backups, drift and stale-documentation reporting.

- [ ] Record PowerShell sessions using supported logging; capture command, timestamp, exit status, working directory, bounded output and session ID.

- [ ] Provide pause/stop controls, retention settings, exclusion lists and secret redaction.

### Stage 2 — Remote state collectors
- [ ] Proxmox API inventory and configuration snapshots.

- [ ] Correlate ordered commands, screenshots, logs and before/after snapshots.

- [ ] Mark procedures as documented, rebuildable, restorable or tested.

- [ ] Export a portable Markdown documentation bundle.

## Definition of done for a recovery procedure

A procedure is not complete merely because Markdown was generated. It must identify its target and prerequisites, preserve command order where known, distinguish facts from inference, link evidence, protect secrets, include verification checks and state whether the procedure has been tested. Any unverified assumptions must be explicit.
